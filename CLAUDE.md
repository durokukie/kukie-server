# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Kukie server — Kotlin 2.3 / Spring Boot 4.1 / Java 25 REST API backed by PostgreSQL (JPA + Flyway) and Redis, with JWT-based authentication.

## Commands

```bash
./gradlew build                # compile + test
./gradlew test                 # run all tests
./gradlew test --tests "com.duro.kukie.global.security.AuthAnnotationConventionTest"   # single test class
./gradlew bootRun              # run the app (spring-boot-docker-compose starts postgres/redis from docker-compose.yaml automatically)
```

- Integration tests use Testcontainers (PostgreSQL + Redis, wired via `TestcontainersConfig`) and the `test` profile (`src/test/resources/application-test.yaml`), so Docker must be running.
- Runtime env vars come from `.env` (see `.env.example`): `JWT_SECRET`, `GITHUB_CLIENT_ID/SECRET`, `GOOGLE_CLIENT_ID/SECRET`, `WEB_APP_URL` (link target of mail buttons) — every OAuth value and `WEB_APP_URL` are `@NotBlank`, so the app fails to start if any is missing or empty. Mail goes out through AWS SES (`aws.region`, `aws.ses.*`); credentials come from the SDK default chain (`AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY` or the `~/.aws` default profile locally, an IAM role via IRSA when deployed — the chain's web identity step needs the `sts` module, which is why it is a dependency). The same chain signs `sts:AssumeRole` into customers' `KukieAccess-*` roles for EKS (`cluster.aws.*`, defaults in `application.yaml`). Also required: `KUKIE_INTERNAL_TOKEN` (`internal.token`, shared with the agent; `@NotBlank`) and `KUKIE_CREDENTIAL_KEY` (`cluster.credential-key`, base64 of exactly 32 bytes — `openssl rand -base64 32`; `AesGcmCredentialCipher` refuses to start otherwise). Optional: `AUTH_COOKIE_SECURE=false` for local http, `AWS_REGION` (default `ap-northeast-2`), `KUKIE_ALLOW_LOCAL_CLUSTER=true` to allow private/loopback cluster addresses (local kind only; default false).

## Architecture

This server is the **Kukie API server**: the only service that talks to the database. kukie-agent runs workflows (LLM loop, guardrails, kubectl) and stores/reads everything through this server's `/internal/**` API.

Package layout is **feature-first** (`user`, `auth`, `team`, `inbox`, `notification`, `cluster`, `chat`, `actionplan`) with a shared `global` package. Each feature follows the same three layers:

- `presentation/` — `@RestController` + request/response DTOs (`dto/request`, `dto/response`). DTOs carry Bean Validation annotations (`@field:NotBlank` etc.) with **no custom messages** — the global handler surfaces the default message. There is no Jackson Kotlin module: request bodies bind through the primary constructor by parameter name, so **Kotlin default values are ignored** — a missing non-null field (including a primitive `Boolean`) is a 400, and every optional field must be nullable (`shared: Boolean? = null`, defaulted in `toCommand`).
- `application/` — one service class **per use case** (e.g. `LogInService`, `CreateUserService`). Every service exposes exactly one public entry point, and it **must** be `operator fun invoke(...)` (called like `logInService(request)`) — never a named method like `createUser()`. Helper functions stay `private`.
  - A service whose input is the request body alone takes the request DTO as is — unless a field must become a domain type (e.g. an email string → `Email`), in which case it also takes a `<UseCase>Command` built by `toCommand()` (e.g. `logInService(request.toCommand())`). When the body must travel with a path variable, query parameter, or `@AuthUser` id, they are merged into one `application/port/in/<UseCase>Command` data class (no validation annotations), built by the request DTO's `toCommand(...)` — e.g. `inviteTeamMemberService(request.toCommand(teamId, userId))`. Services without a body keep plain parameters.
- `domain/` — JPA entities and repository **abstractions** only. Spring Data interfaces (e.g. `UserRepository`) live here; Redis-backed stores are declared here as plain interfaces (`RefreshTokenRepository`, `VerificationCodeRepository`).
- `infrastructure/` — implementations of the domain repository interfaces (e.g. `RedisVerificationCodeRepository`, `RedisRefreshTokenRepository`): `@Repository` classes over `StringRedisTemplate` with key prefixes and TTLs. Technology details (Redis templates, TTLs) belong here, not in `domain/`.
- `exception/` — per-feature `ErrorCode` enum (implements `global.exception.ErrorCode`; `code` = enum name, Korean messages) plus one `BusinessException` subclass per error. `GlobalExceptionHandler` converts these to `ErrorResponse(code, message)`.

### Authentication flow (global/security)

Not Spring Security — a custom interceptor-based mechanism:

- `@Authenticated` on a controller class or handler method marks it as requiring auth; `AuthenticationInterceptor` resolves the access token — `Authorization: Bearer` header first, else the `__Host-kukie_access` cookie — validates it via `JwtTokenProvider` and stashes the user id as a request attribute. Header wins when both are present (a blank header counts as absent; a present-but-malformed header is a 401, never a cookie fallback). Cookie auth is accepted only when the browser's `Sec-Fetch-Site` is `same-origin` or `none` — `same-site`, `cross-site` or missing → 403 `CROSS_SITE_COOKIE` (fail-closed; `SameSite=Lax` alone lets top-level GETs through; the web client shares this server's origin via the reverse proxy). Browsers send that header only on HTTPS/localhost, so web login presumes an HTTPS deployment (the cookies are `Secure` anyway). The agent sends Bearer; the web client (in a browser or inside the Electron shell, which loads the same web page) relies on cookies.
- Login/refresh responses return tokens **both** as JSON and as httpOnly cookies (`__Host-kukie_access`, `__Host-kukie_refresh`; `Secure`, `SameSite=Lax`, `Path=/`, no `Domain`, max-age = token expiry) via `AuthCookies` — no per-client branching. `/auth/refresh` reads the refresh token from the body, else from the cookie; `/auth/logout` clears both cookies. Cookie names/`secure` live in `AuthCookieProperties` (`auth.cookie.*`); the names actually used are `accessCookieName`/`refreshCookieName`, which add `__Host-` when `secure` is true (plain names with `AUTH_COOKIE_SECURE=false`, since browsers reject `__Host-` without `Secure`). The prefix keeps user apps on sibling subdomains (`*.apps.durokukie.com`) from shadowing these cookies with `Domain=durokukie.com`, so reads accept **only** the prefixed name — never fall back to the plain one. Login/refresh/logout also expire the old unprefixed cookies. The agent reads the access cookie too (`KUKIE_ACCESS_COOKIE`), so a name change must be mirrored there.
- `@AuthUser userId: UUID` handler parameters are resolved by `AuthUserArgumentResolver` (parameter must be `UUID`).
- **Convention enforced by test**: `@AuthUser` may only appear on handlers covered by `@Authenticated` (`AuthAnnotationConventionTest`).
- **Internal API** (agent → `/internal/**`): `@InternalApi` on the class or handler; `InternalApiInterceptor` (registered before `AuthenticationInterceptor`) compares `X-Kukie-Internal-Token` with `internal.token` via `MessageDigest.isEqual` → 401 `INVALID_INTERNAL_TOKEN`. `InternalApiConventionTest` enforces that every handler under `/internal` has `@InternalApi` and no other handler does. The reverse proxy must not expose `/internal` publicly.
  - **Entry vs non-entry**: the user's token is taken **once, at the entry** of a request, where the server judges "may this user do this to this conversation/cluster". Entry handlers also carry `@Authenticated` and receive the user's Bearer: conversation `context?purpose=chat|approve`, `runs/by-request/{requestId}`, `POST conversations/{id}/runs`, cluster `connection`. **Every other internal handler takes the internal token only** and finds its target by `runId`/`planId`/`conversationId` (run update, interrupt, interrupt-orphaned, plan create/list/get and actions, cluster status) — an access token lives 30 minutes, and a run that outlives it must still record its kubectl results. Never add `@Authenticated`/`@AuthUser` to a non-entry handler.
- Access/refresh tokens are typed via a `type` claim; refresh tokens are stored in Redis and rotated on refresh. Expirations configured under `jwt.*` in `application.yaml`.

### OAuth (auth feature)

- **The only OAuth client is the web page** (opened in a browser or inside the Electron shell). It uses the authorization code flow with PKCE: the provider redirects the browser to `<origin>/auth/callback` (a front-end route, not an endpoint of this server), and the page POSTs `code` + `redirectUri` (+ `codeVerifier`) to `/auth/oauth/{provider}`, which exchanges the code using the client secret. The old native desktop flow (loopback redirect on `http://127.0.0.1:<port>`, a separate desktop credential pair) is gone.
- **One credential pair per provider** (`OAuthProperties`: `github` and `google` are each a `Credential(clientId, clientSecret)` bound from `oauth.<provider>.client-id/client-secret`). Both are required at startup — any missing or blank value fails startup (`@Validated` + `@NotBlank`; compose passes absent vars as empty strings). The front end's `VITE_*_WEB_CLIENT_ID` must be the same client, or the exchange fails.
- **Google**: a **"Web application" type** client with every callback URI registered (`https://<deployed origin>/auth/callback`, `http://localhost:5173/auth/callback` for local dev).
- **GitHub**: one OAuth App with the same callback URLs registered (an OAuth App can hold several).

### Clusters (cluster feature)

- Every cluster belongs to a team (`team_id NOT NULL`; there are no personal clusters). Paths carry no `{teamId}`, so `ClusterPermission` checks membership in the service: readable by current team members, writable by team ADMINs (`NOT_TEAM_ADMIN`). Unreadable clusters are 404 `NOT_FOUND`, never 403.
- Uploaded kubeconfigs go through the `KubeconfigParser` port (`SnakeYamlKubeconfigParser`, a port of the agent's `kubeconfig.py`): rejects exec/auth-provider, file-path references, non-inline data and private/loopback/link-local/reserved addresses, including what the host name resolves to (`HostResolver`). Rejection messages are user-facing (`KUBECONFIG_REJECTED` carries the reason).
- Name resolution can hang (getaddrinfo has no timeout), so `SystemHostResolver` runs lookups on its own 4 threads (the agent's `RESOLVE_WORKERS`) and waits at most 5 s; a lookup that times out is rejected (an unknown name, NXDOMAIN, resolves to nothing and passes, as in the agent). Register/update parse the kubeconfig **outside any transaction** so no DB connection is held during DNS (this relies on `open-in-view: false`); `UpdateClusterService` checks permission first, then re-reads the cluster and writes in a short `TransactionTemplate` transaction so it never writes back values read before the lookup.
- Credentials are stored only as AES-256-GCM ciphertext (`CredentialCipher`); plaintext leaves the server only via the internal `connection` endpoint. Public responses never include credentials.
- **EKS via the customer's AWS account** (`provider = EKS`, `AwsClusterController` under `/clusters/aws`, team ADMIN only):
  1. `POST /clusters/aws/connections {teamId}` issues an `AwsConnection` (`tbl_aws_connection`): **one row per customer AWS account** (V16; a team may connect several, `(team_id, account_id)` unique while connected). A row is *pending* (`accountId` and `lastAccountId` null) until a stack notice verifies it, and the call returns the team's oldest pending row if there is one, else a new row. `GET /clusters/aws/connections?teamId=` lists the team's rows; the others take the row's id and use its team. ExternalId `kukie-` + 16 hex chars (SecureRandom). The response carries a CloudFormation quick-create link for the public template `cluster.aws.template-url` (published by kukie-infra), which creates role `KukieAccess-<ExternalId>` in the customer's account. That role trusts only this server's IRSA role (`kukie-dev-member`) with that ExternalId and may manage only its own EKS access entry, with `AmazonEKSEditPolicy` on exact namespaces within the stack's `AllowedNamespaces` (no `*`/`?`, no `kube-*`). The IRSA role's `sts:AssumeRole` on `arn:aws:iam::*:role/KukieAccess-*` (ExternalId required) is defined in kukie-infra.
  2. `POST /clusters/aws/candidates {connectionId, accountId}` assumes the role and lists EKS clusters in `cluster.aws.regions` (404 `AWS_CONNECTION_NOT_STARTED` for an unknown row; 409 `AWS_ACCOUNT_MISMATCH` when the row is connected to another account — a pending row takes the given account, as v1 stacks send no notice).
  3. `POST /clusters/aws {connectionId, accountId, region, clusterName, namespace, name}` checks the account like step 2, validates the namespace (DNS-1123 label, not `kube-*` → `INVALID_NAMESPACE`) and region, describes the cluster, runs its endpoint through the same address check as kubeconfigs (`ApiServerAddressChecker`, honoring `KUKIE_ALLOW_LOCAL_CLUSTER`), creates the role's access entry and associates the Edit policy for the namespace (merging namespaces already associated, since re-associating replaces the scope), then saves the cluster. Like kubeconfig registration it runs outside any transaction.
- An EKS cluster stores no secret: its `credential` ciphertext holds `{type: eks, accountId, externalId, region, clusterName}` (`EksCredential`). On every internal `connection` call `GetClusterConnectionService` assumes the role (session `cluster.aws.session-seconds`, cached by `AwsEksAccessGateway` while more than 5 minutes remain) and returns a fresh EKS bearer token as `credential = {token}` — the same shape as a token kubeconfig, so the agent needs no change. The token is what `aws eks get-token` produces: an STS `GetCallerIdentity` URL presigned (60 s) with `x-k8s-aws-id: <cluster>` signed in, by `EksTokenSigner` (SDK `AwsV4HttpSigner`), prefixed `k8s-aws-v1.` and base64url-encoded without padding. Never log the assumed credentials or the token.
- `GET /clusters/{id}/setup` (readable by team members) returns the EKS version, endpoint access, service CIDR, add-ons, node groups and subnets (zone + CIDR only) for the cluster map. Add-ons/node groups/subnets need template v3 permissions (`eks:ListAddons`/`DescribeAddon`/`ListNodegroups`/`DescribeNodegroup`, `ec2:DescribeSubnets`); a v1/v2 role's AccessDenied (EC2 `UnauthorizedOperation`) becomes `status: permission_required` with empty lists, and a non-EKS cluster is `unsupported`.
- `DELETE /clusters/aws/connections/{connectionId}` (team ADMIN; 404 `AWS_CONNECTION_NOT_STARTED`) disconnects that one account: Kukie cannot delete the customer's stack (no permission, and the role would delete itself), so it removes its access entry once per EKS of the team registered with that row's ExternalId (same account/ExternalId/region/cluster name, `keepNamespaces` empty; best effort, failures logged by class name only), clears the connection's `accountId`/`connectedAt`/`stack_id` (V12, the ARN from the stack notice, kept only when it belongs to the verified account), keeps the cluster registrations and the ExternalId, and returns `{stackConsoleUrl, stackName}` — the stack's CloudFormation console page (`StackConsoleUrl`), or for connections made before V12 the stack list filtered by name in `cluster.aws.console-region`. AWS calls run outside any transaction. A later `Create` stack notice for the same ExternalId (after a disconnect, or after the customer deleted the stack directly in the console) re-attaches each of the team's EKS in that account: `unregisterSelf` with no namespaces first — the old entry is bound to the deleted role's unique ID and `registerSelf` would keep it on `ResourceInUse` — then `registerSelf` per registered namespace (best effort per EKS, after replying to CloudFormation). Before verifying, a stack notice is refused (FAILED, so CloudFormation rolls the role back) when its row is connected to a different account (the same link run in another account) or another row of the team is connected to that account. The list also returns `stackConsoleUrl` while connected. After a disconnect, `disconnect()` moves the account/stack ARN to `last_account_id`/`last_stack_id` (V13; a reconnect clears them) and the list keeps returning `stackName`/`stackConsoleUrl` plus `stackDeleted` for that row, found by assuming the old role directly (`EksAccessGateway.roleExists`, bypassing and evicting the session cache; 403 = deleted, other errors = `null`) since CloudFormation's Delete notice arrives before the role is gone; a confirmed deletion is stored in `last_stack_deleted_at` (conditional update, so a reconnect in between is not overwritten) and STS is not called again.
- EKS clusters can only be renamed: a kubeconfig or namespace change is 400 `CLUSTER_PROVIDER_MISMATCH` (the access policy is bound to the registered namespace). Assumed-role sessions are cached per `AwsTarget`; a stack notice's `verify` re-assumes (the role may have been re-created), and every EKS/EC2 call goes through `withSession`, which on an invalid-session error (`UnrecognizedClientException`, `InvalidClientTokenId`, `ExpiredToken(Exception)`, EC2 `AuthFailure`, or the "security token included in the request is invalid" message) evicts the session and retries once. AWS failures map to `AWS_ROLE_NOT_ASSUMABLE` (AssumeRole 403, or a session still invalid after that retry), `EKS_CLUSTER_NOT_FOUND`, `EKS_ACCESS_DENIED` (e.g. a namespace outside `AllowedNamespaces`), `EKS_ACCESS_ENTRY_DISABLED` (authentication mode `CONFIG_MAP`) and `EKS_CLUSTER_NOT_READY`.

### Chats and Action Plans (chat · actionplan features)

- A chat is `ChatSession` (`tbl_chat_session`; the API keeps the path `/conversations` and the JSON names `conversation`/`conversationId`); each user request is a `ChatRun` (`tbl_chat_run`); each mutating tool call is an `ActionPlan` (`tbl_action_plan`). A session always has a cluster (`cluster_id NOT NULL`) and its team is the cluster's team (no `team_id` column). Context, namespace and fingerprint are copied from the cluster at creation. Status strings are the agent's wire values (`running`/`awaiting_approval`/…, `DRAFT`/`WAITING_APPROVAL`/…); lowercase enums use a `@JsonValue` + `@Converter(autoApply = true)` pair like `ClusterStatus`.
- `ChatPermission` holds the read/approve rules by `ChatVisibility` (private → owner only; shared → current team members; approve also needs shared + a current member who is ADMIN or the owner → `PRIVATE_SESSION` / `NOT_TEAM_ADMIN`). Unreadable conversations and plans are 404 `NOT_FOUND`. The list queries (`ChatSessionRepository.findAllVisibleTo`, `ActionPlanRepository.findAllVisibleTo`) must apply the same rule — keep them in sync. `GET /conversations/{id}` is a pure read.
- **Run start** (`StartRunService`) locks the session row (`PESSIMISTIC_WRITE`), replays the same `requestId` (409 `REQUEST_MISMATCH` if kind/input differ), refuses a second active run (409 `ACTIVE_RUN_EXISTS`; the partial unique index `uk_chat_run_active` is the DB backstop) and bumps the session `version`. Lock order is session → run → plan everywhere (`UpdateRunService` looks up the session id first); team deletion takes the same order from the top (team → clusters → sessions → runs) before it deletes anything.
- **Run update** (`PATCH /internal/runs/{runId}`) is one transaction: field updates, appending `agentMessages`, `finishedAt`, closing the run's open plans (`ActionPlanRepository.closeOpenPlans` → `ActionPlan.close`: approved without result → `UNKNOWN`, else `EXPIRED`), the session mode and the first-message title (`FirstMessageTitle`, ported from the agent's `name_from_first_message`).
- **The server owns the plan state machine** (`ActionPlan` methods, ported from the agent's `guardrail/action_plan.py`). The agent reports what happened through action endpoints (`dry-run`, `offer`, `decision`, `start`, `result`, `fail`, `unknown`); there is no generic PATCH. Each action service locks the plan row (`lockByIdOrThrow`) before checking preconditions, so concurrent duplicates succeed once; a disallowed action is 409 `PLAN_STATE_CONFLICT`, an approval whose call differs from the plan is 409 `PLAN_CALL_MISMATCH`. Plan codes (`ap-YYMMDD-HHMM-<tool>[-N]`, UTC) are picked under a per-minute advisory lock (`lockCodeGeneration`).
- Plan detail markdown is rendered here (`ActionPlanMarkdownRenderer` port, `SnakeYamlActionPlanMarkdownRenderer`), structurally equal to the agent's `render_markdown`.
- Deleting a team deletes, in one transaction and in FK order, its plans → runs → sessions → clusters, then its AWS connection, invitations/memberships/team (`DeleteTeamService`; no `ON DELETE CASCADE` so a future retention policy changes one place). Before deleting it locks the team row, then its clusters, sessions and runs (`lockIdById`/`lockIdsByTeamId`, native `FOR UPDATE ... ORDER BY id`): deleting plans first would deadlock with a run update holding the run and waiting on its plans, and a row inserted meanwhile under one of those locks (a plan, run, session or team cluster) would fail the delete with an FK violation. Deleting a cluster that still has conversations is 409 `CLUSTER_IN_USE`.

### Persistence

- Entities extend `BaseTimeEntity` (JPA auditing `createdAt`/`updatedAt`), use time-ordered UUIDv7 ids (`UuidCreator.getTimeOrderedEpoch()`), `protected set` properties, and encode passwords in the constructor (entity takes `rawPassword` + `PasswordEncoder`).
- Schema is managed by **Flyway** (`src/main/resources/db/migration`, `V<n>__Description.sql`); Hibernate runs with `ddl-auto: validate`, so any entity change needs a migration. Tables are prefixed `tbl_`.
- `spring.jpa.open-in-view` is **false**: a DB connection is borrowed only for a transaction or a single repository call, never for the whole request (slow DNS or mail would otherwise drain the pool). Entities loaded outside a service transaction are detached — do not rely on lazy loading or dirty checking there; put reads and writes that belong together in one transaction.
- Repository "find or throw" helpers are extension functions (e.g. `UserRepository.findByIdOrThrow`).
- **jsonb**: opaque agent JSON (`responsePayload`, `agentMessages`, `usageSummary`, plan `payload`/`decision`/`executionResult`) is mapped with `@JdbcTypeCode(SqlTypes.JSON)` on plain `Map<String, Any?>`/`List<Any?>` and returned as stored — keys are never renamed (snake_case stays snake_case; Postgres jsonb only normalizes key order and whitespace). jsonb rejects NUL (`\u0000`) in strings, which kubectl output can carry, so the entity methods pass agent JSON through `global.util.withoutNul()` (NUL → U+FFFD, keys included) and `ActionPlan` compares approval calls the same way. Hibernate currently picks its Jackson 2 `JacksonJsonFormatMapper` (Jackson 2 is on the classpath transitively); plain maps/lists work the same with its Jackson 3 mapper. Replace a JSON value as a whole instead of mutating it in place.
- New time columns (`startedAt`, `finishedAt`, `appliedAt`) are written in UTC (`global.util.utcNow()`); `at` values inside opaque JSON are `2026-10-14T09:00:00Z` strings. Auditing (`createdAt`/`updatedAt`) uses the JVM default zone, which is UTC in the container image.
- Email addresses are `global.domain.Email` (a `@JvmInline value class`; `Email(raw)` trims + lowercases), never `String`, in entities and repositories; request/response DTOs and mail ports keep `String` (`email.value`). The request DTO's `toCommand(...)` does the conversion, so commands carry `Email` and services never wrap request strings (in such DTOs write the validation annotation as `@field:jakarta.validation.constraints.Email` to avoid the name clash). Exceptions: `SendVerificationCodeService` takes a single `Email` built by the controller, and `OAuthLogInService` wraps the provider's profile email. It is stored as a plain `varchar` and values read from the DB are not re-normalized, so the DB must hold only normalized addresses (see V6). Keep JPA annotations on fields: property access would hit the mangled getters (`getEmail-…`).

## Testing

- Test method names are Korean sentences in backticks (`` fun `로그인에 성공하면 토큰을 발급하고 리프레시 토큰을 저장한다`() ``) with `// given` / `// when` / `// then` comments.
- **Test ordering**: within each use case (API/service being tested), the success case comes first, followed by its exception cases.
- **Unit tests** (`*ServiceTest`, `JwtTokenProviderTest`): no Spring context — MockK (`@ExtendWith(MockKExtension::class)` with `@MockK`/`@SpyK`/`@InjectMockKs`) plus kotest assertions (`shouldBe`, `shouldThrow`).
- **Integration tests** (`*IntegrationTest`): extend `support/IntegrationTest`, which boots the full app (`@SpringBootTest` + MockMvc) against Testcontainers and replaces the mail senders with `FakeVerificationCodeSender`/`FakeTeamInvitationSender` (`@Primary`; read sent codes via `lastCodeFor(email)`). It also replaces `HostResolver` with `FakeHostResolver` (fixed public address; set `addresses` to simulate a private one, `onResolve` to act during a lookup) so kubeconfig checks never hit real DNS. The base class provides `mockMvc`, `loggedInUser()` (persists a user and issues real tokens), `savedTeam(userId to role, …)`, `Any.toJson()`, and `authorization(accessToken)` / `internalToken()` DSL helpers, and after each test truncates all tables and flushes Redis — individual tests never clean up. Use the MockMvc Kotlin DSL (`mockMvc.post("/users") { ... }.andExpect { ... }`).
- Entity test data comes from fixture objects with overridable defaults (`UserFixture.user()`, `ChatFixture`, `ActionPlanFixture` — whose `offered()`/`approved()`/`executing()` extensions walk a plan through real transitions).
- **Concurrency tests** (`TeamPermissionConcurrencyTest`, `RunStartConcurrencyTest`, `ActionPlanConcurrencyTest`, `TeamDeleteConcurrencyTest`): MockMvc does not reproduce races, so open overlapping transactions with `TransactionTemplate` + latches, or fire the service from a thread pool, and assert exactly one winner (or, for team deletion, that both sides finish). To wait until the other side is blocked on a row lock, poll `pg_stat_activity` (`wait_event_type = 'Lock'`) from a connection outside that transaction.

## Conventions (from CONTRIBUTING.md)

- Git flow without release branches: PRs target `develop`; branch names are `<feat|fix|refactor|hotfix>/<kebab-description>-<issue#>` (e.g. `feat/chat-session-12`).
- Commit messages: `<type>: <subject>` with types `feat|fix|refactor|docs|style|test|chore`, imperative subject, optional scope (`feat(auth): ...`). Commit subjects and code messages are written in Korean.
- Code style follows the official Kotlin Coding Conventions.
- Comments: write one only for a constraint the code cannot show and a reader would likely break without it (e.g. a lock order), as a single short line. Do not restate the code, cite planning docs or issue numbers, or narrate design history. Test `// given` / `// when` / `// then` markers are the exception.
